## 🔴 Нашёл новый серьёзный баг — пароли уходят в браузер

Проверил конкретно:

```js
// строка 70
const result = await pool.query('SELECT * FROM users WHERE login = $1', [login]);
...
return res.json({ success: true, user: user });   // весь объект user, включая password_hash!

// строка 100
router.get('/users', ... 'SELECT * FROM users ORDER BY id ASC');  // тоже весь объект
```

Это значит: bcrypt-хеш пароля **каждого пользователя** реально прилетает в браузер каждый раз, когда:
- кто-то логинится (ответ на `/login`),
- открывается справочник "Пользователи",
- заполняется любой выпадающий список, где используется `/api/users` как источник.

Во фронтенде хеш просто визуально скрыт (`style="display:none"`), но это не защита — он виден в Network-вкладке DevTools у любого пользователя системы. Хеш можно унести и брутфорсить офлайн.

**Исправление простое:**
```js
'SELECT id, login, name, description FROM users WHERE login = $1'
```
Никогда не выбирайте `password_hash` в ответах, кроме внутренней проверки в `/login` (и даже там — выберите его отдельно, не возвращайте наружу).

## 🔴 Смена пароля пользователя тихо ломается

Я проверил: специального `PUT /api/users/:id` нет — редактирование пользователя идёт через универсальный `router.put('/:entity/:id')`, который **не хеширует** `password_hash` — просто пишет то, что пришло, как есть.

Сейчас это не стреляет только потому, что фронтенд физически скрывает поле пароля при редактировании (`if (entity === 'users' && col.field === 'password_hash' && item.id) return '';`). То есть это не баг, который сработал, а мина: если кто-то потом добавит форму "сменить пароль" через этот же путь, или отправит `PUT /api/users/5 {"password_hash":"1234"}` вручную через curl — пароль сохранится в БД открытым текстом, и следующий логин сломается (bcrypt.compare не совпадёт с "1234").

Заодно это значит: **сейчас пользователи вообще не могут сменить себе пароль** через интерфейс — это баг продукта, не только безопасности.

## 🔴 Подтверждаю: авторизации на API нет вообще

Проверил все 122 роута — ни один (кроме самого `/login`) не проверяет ни токен, ни сессию. `x-user-id` — это просто число, которое браузер сам вписывает в заголовок и присылает добровольно:
```js
const currentUserId = req.headers['x-user-id'] || req.headers['user-id'] || null;
```
Любой человек с `curl` может читать/писать/удалять что угодно без пароля, а заодно вписать в лог аудита любой `user_id`, какой захочет (то есть логи аудита нельзя доверять — их легко подделать).

## 🔴 Universal POST/PUT — нет вайтлиста полей

Проверил напрямую:
```js
const keys = Object.keys(req.body);
...
const query = `INSERT INTO "${entity}" (${columns}) VALUES (${placeholders})`;
```
Имя таблицы проверяется (`allowedTables`) — это хорошо. Но **колонки — нет**. В тело запроса можно вписать любое поле любой разрешённой таблицы, включая то, что не должно задаваться руками (например, `is_posted` при создании нового документа в обход бизнес-логики).

## 🟠 Реальное дублирование кода в api.js — подтверждено построчно

Не "как будто", а буквально одинаковые функции объявлены по несколько раз:
- `writeMoveLog` — 3 раза
- `writeRepairLog` — 4 раза
- `writeRealizationLog` — 3 раза

Я сверил содержимое — копии идентичны (не разошлись), так что прямо сейчас багов от этого нет. Но это мина: если через полгода понадобится поправить логику логирования ремонта, есть 4 места, и легко забыть одно — тогда поведение будет непредсказуемо зависеть от того, какое объявление "выиграло" (последнее по файлу, из-за hoisting).

## 🟠 Загрузка файлов всё ещё без ограничений

```js
const upload = multer({ dest: path.join(__dirname, '../uploads/') });
```
Нет `limits.fileSize`, нет `fileFilter` по типу. Можно залить файл любого размера и любого типа в папку `/uploads`, которая раздаётся статически — то есть потенциально можно закинуть что угодно и получить прямую ссылку на него.
